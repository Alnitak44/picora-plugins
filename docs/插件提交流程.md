# 插件提交流程

Picora 的[插件仓库](https://github.com/Alnitak44/picora-plugins)收录插件登记信息。所有插件的源码和 ZIP 都由作者在自己的独立公开 GitHub 仓库维护；目录仓库不托管插件 Release。首次收录提交一份登记文件，后续版本由插件仓库从 GitHub Release 自动获取。

## 首次投稿

1. 按 [插件协议](PLUGINS.md)制作插件，在 Picora 中用本地 ZIP 测试。新插件 ID 使用 `io.github.<GitHub 用户名小写>.<插件名>`，并保持稳定。ZIP 根目录需有 `plugin.json`、入口 JSON、`readme.md` 及所引用的资源。
2. 在自己的公开 GitHub 仓库发布 Release，将 `.picora-plugin.zip` 文件上传为 Release 附件。Release 标题可自定；建议标签与插件版本对应，例如 `v1.0.0`。不要只依赖 GitHub 自动生成的 Source code ZIP。
3. Fork [插件仓库](https://github.com/Alnitak44/picora-plugins)，参考 [通用登记示例](https://github.com/Alnitak44/picora-plugins/blob/main/examples/io.github.example.picora.demo.json)，新增 `registrations/<插件 ID>.json`，然后向插件仓库的 `main` 分支提交 PR。登记文件需填写：
   - `id`：与 ZIP 内 `plugin.json` 的 ID 完全一致。
   - `releaseRepository`：作者的 `用户名/仓库名`；`plugin.json` 的 `repository` 应指向同一仓库。
   - `minAppVersion`：插件要求的最低 Picora 版本；`http-v2` 至少为 `1.0.1`。
   - 属性标签：不用填写。目录会从 ZIP 推导：配置字段的 `role`（`token` / `account` / `endpoint`）生成对应标签，多登录方式的 `authModes[].config` 同样参与推导，根级或任一方式的 `delete` 请求自动带「云删除」，版本号带 `-beta` 之类的预发布后缀自动带「测试版」。规则见[插件开发文档](PLUGINS.md#属性标签)。使用 `role` 时 `minAppVersion` 至少为 `1.0.8`，使用 `authModes` 时至少为 `1.1.0`。暂无配置字段却需要凭证的插件，可临时写 `tags` 兜底，补上 `role` 后应删除。
   - `approvedPermissions`：与入口 JSON 的 `permissions` 对应，尤其要准确列出网络目标。
   - `allowedLinks`（可选）：教程或主页确实需要指向第三方域名时，在这里列出主机名，例如 `["docs.example.org"]`；只有审核过的域名才会被放行。
4. PR 的 CI 从 Release 读取 ZIP，验证包结构、ID、版本、运行时和权限。维护者审核后合并；插件仓库自动生成客户端读取的 `index.json` 和插件列表。

投稿时无需填写下载地址、ZIP 大小或 SHA-256，也无需将 ZIP 或源码复制到插件仓库。

## 名称、内容与链接要求

名称、简介、作者和 `readme.md` 会随新版本自动同步到目录，所以这几项在每次构建时都会被检查，命中即构建失败：

- **文案**不能出现引流、诈骗类内容（加联系方式、领红包、破解激活、代充、赌博等）。这类词表由维护者维护，命中会直接拒绝，不会静默改写。
- **链接**：`readme.md` 与 `homepage` 只能指向 GitHub 平台、该插件自身已批准的请求主机（含同一主域），或登记文件 `allowedLinks` 中审核过的域名。`example.com` 等占位域名和 `https://你的域名` 这类中文占位写法不校验。教程里的链接用户会直接点击打开，因此不接受任何未审核域名。
- 使用 `network: ["*"]`（通配主机，常见于自建服务）的插件在构建时会输出警告，这类插件可以改写请求目标，首次收录与权限变更时需要人工确认。

## 发布更新

保持插件 ID 不变，在作者仓库发布版本号递增的新 Release，并上传新的 `.picora-plugin.zip` 附件。插件仓库定时检查 Release；验证通过后自动更新目录。不要用不同内容覆盖已发布版本的附件。

作者仓库必须保持公开可访问：删除仓库或改为私有会触发[自动注销](#自动注销作者删库)，不会为你保留目录条目。

插件名称、作者、简介、图标、颜色和版本都取自 ZIP 内的 `plugin.json`，登记文件里没有这些字段。因此改名、换作者、改简介只要随新版本发布即可自动同步，不需要提 PR；反过来，只改源码仓库不发 Release 不会影响目录。

如果新版本改变了网络目标、不安全 HTTP 或云端删除权限，应先修改插件仓库中的登记文件并提交 PR，说明变化，等待审核；审核通过后再发布新 ZIP。Picora 用户安装更新时仍会看到插件的实际权限。

开始使用 `http-v2`、条件 JSON 字段、`config[].role`、`config[].input`、`authModes` 等新能力时，也要提 PR 抬高 `minAppVersion`。目录只校验该字段是否存在，不会推导所需版本；写低了会让旧客户端在安装阶段拒绝插件。

## 退出收录

开发者可以随时申请将自己的插件移出插件仓库，退出理由可选。

1. 删除插件仓库中的 `registrations/<插件 ID>.json`，提交 PR，注明“退出收录”及插件 ID。不要直接修改自动生成的 `index.json` 或插件列表。
2. 不便提交 PR 时，也可以在[插件仓库发起 Issue](https://github.com/Alnitak44/picora-plugins/issues/new)，附上插件 ID、源码仓库链接并提出移除申请。
3. 维护者核实请求者为插件作者或获授权的维护者后处理。登记移除并成功生成新目录后，插件停止在线展示、下载和更新；客户端成功刷新目录后生效，已有缓存或镜像可能延迟。

退出收录不会卸载用户已安装的插件，也不会删除配置、上传记录或图床文件。作者的源码仓库和 Release 仍由作者自行管理，已获取 ZIP 的用户仍可本地安装。

### 自动注销（作者删库）

目录只跟随作者仓库的公开 Release 工作。作者仓库被删除或转为私有后，插件会被自动注销，不需要再走上面的申请流程：

1. 构建请求该仓库的 Release 时 GitHub 返回 404；
2. 目录改用仓库接口 `/repos/<用户名>/<仓库名>` 二次确认，只有仓库确实不可访问才判定为注销，避免把临时故障当成删库；
3. 判定成立后，该插件从 `index.json` 与 README 列表移除，对应的 `registrations/<插件 ID>.json` 由工作流一并删除并提交，日志输出 `已不存在（GitHub 返回 404），按作者注销处理`。

声明与边界：

- 注销由目录自动执行，不单独通知作者，登记文件被删除后不会自动恢复。
- 已安装该插件的用户不受影响：本地插件、配置、上传记录和图床文件都不会被删除，只是不再收到更新。
- 以下情况**不会**自动注销，构建会失败并等待人工处理：合规封禁（HTTP 451）、API 限流（403）、网络或 TLS 故障、仓库改名后附件地址不匹配，以及其他非 404 异常。
- 恢复收录时，按首次投稿流程重新提交登记文件并接受审核。

## 目录如何工作

客户端从插件仓库的 `main/index.json` 读取目录，下载 GitHub Release 中的插件 ZIP。目录缓存 12 小时，可手动刷新；连接失败时使用上次有效目录。GitHub 镜像仅在客户端下载目录和 ZIP 时应用，不用于图床上传或插件认证。

`index.json` 由插件仓库生成，包含插件元信息、下载地址、ZIP 字节数与 SHA-256，供客户端核对身份和完整性。投稿者只编辑登记文件，不直接修改 `index.json`。插件源码与许可证归作者维护；目录合并由维护者审核请求目标、凭证使用及删除语义。

目录还会为每个插件记录 GitHub 仓库的数字 ID（`repositoryId`，客户端忽略该字段）。仓库改名或转移到别的账号时 ID 不变，目录会按新名称自动继续收录；如果同名仓库的实际 ID 发生变化（改名后被他人重新注册），构建会失败并等待人工确认，避免把别人的仓库当成插件源。

## 常见问题与排查

| 现象或报错 | 检查与处理 |
| --- | --- |
| `no matching published ZIP release` | 确认作者仓库已发布正式 Release，并上传插件 ZIP；附件名必须以 **`.picora-plugin.zip`** 结尾，区分大小写。例如 `imgloc-1.1.0.picora-plugin.zip`，注意版本号后是点号，不能写成 `imgloc-1.1.0-picora-plugin.zip`。草稿、预发布以及 GitHub 自动生成的 Source code ZIP 不会收录。 |
| 附件存在，仍提示找不到匹配插件 | 核对 ZIP 内 `plugin.json` 的 `id` 与登记文件一致；如果登记了 `assetPrefix`，附件名必须以该前缀开头。仓库名、附件基础名称和插件 ID 不要求完全相同。 |
| `filename must match plugin id` | 登记文件应命名为 `<完整插件 ID>.json`，例如 `io.github.alnitak44.imgloc.json`。缺少 `.json` 的文件不会被扫描，也可能出现工作流成功但未收录的情况。 |
| `id must use the GitHub owner's io.github namespace` | 新插件 ID 使用 `io.github.<作者 GitHub 用户名小写>.<插件名>`；登记文件与 ZIP 内保持一致。 |
| `tags` 无效 | 过渡用的 `tags` 必须是数组，元素只能取 `token`、`account`、`custom-url`，且不能重复。插件包内已声明 `role` 时以插件包为准，登记值会被忽略。 |
| `permissions changed; update registration through review` | 登记文件的 `approvedPermissions` 必须与入口程序的 `permissions` 一致。`network` 填主机名，例如 `["imgloc.com"]`，不要填 `["https://imgloc.com/"]`；网络目标和权限变化需重新审核。 |
| `package repository differs from releaseRepository` | `releaseRepository` 填 `用户名/仓库名`；ZIP 内 `repository` 填同一仓库的根地址，例如 `https://github.com/Alnitak44/picora-plugin-imgloc`，不要指向 `/tree/main/…` 子目录。 |
| `ZIP is missing required root files` 或客户端提示缺少文件 | 解压后的根目录应直接包含 `plugin.json`、声明的入口 JSON、`readme.md` 和 `assets/`，不能额外套一层插件目录。Release 的 **Assets** 是上传 ZIP 附件的位置；ZIP 内的 **`assets/`** 存放图标等资源。 |
| `published ZIP changed without a new version` | 修改插件内容后递增 `plugin.json` 的 `version`，发布新 Release 和新 ZIP；版本取自包内元信息，不取自附件名或 Release 标签。仅修改附件名不改变 ZIP 内容。 |
| 工作流成功，软件仍未显示或更新 | 确认登记已合并到插件仓库 `main`，且新的 `index.json` 已生成；再在 Picora 插件仓库点击右上角刷新。客户端缓存与公共镜像可能延迟。 |
| 改了名称、作者或简介，目录没变 | 目录读的是 Release 附件里的 ZIP，不是源码仓库。确认已发布正式 Release、ZIP 内 `plugin.json` 已更新且版本号递增；只改仓库文件不会生效。 |
| 插件在目录里突然消失 | 作者仓库被删除或转为私有会触发[自动注销](#自动注销作者删库)：Release 接口与仓库接口都返回 404 后，目录移除该条目并删除对应登记文件。恢复收录请按首次投稿流程重新提交登记。 |
| `readme.md 里的链接指向 ...` 或 `homepage 里的链接指向 ...` | 教程与主页只能链接 GitHub、插件自身的请求主机或 `allowedLinks` 审核过的域名。删掉无关外链，确需保留就在登记文件加 `allowedLinks` 并提交 PR。 |
| `含违规内容` | 名称、简介、作者或教程出现引流、诈骗类用语。修改文案后递增版本重新发布；词表由维护者维护，不接受为规避检查而做的变体写法。 |

### 查看失败原因与重试

打开插件仓库的 **Actions → Build plugin catalog → 失败的运行 → build**，展开失败步骤。直接提交到 `main` 时通常查看 **Generate catalog**；PR 校验通常查看 **Validate proposed catalog**。查找 `catalog build failed: …` 后面的具体原因，邮件里的“所有任务失败”只是概要。

作者仓库的 Release 或附件修正后，可重新运行失败工作流，也可以手动触发插件仓库的 **Build plugin catalog**。若修改的是登记文件，应提交修正，等待对应工作流完成。客户端暂时显示旧目录不代表校验已经通过，不要手改 `index.json` 绕过校验。
